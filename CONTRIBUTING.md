# Contributing

Thanks for considering a contribution. This is a Kubernetes controller, so most
changes are small and behavioural — the bar is that the behaviour is *demonstrated*,
not just described.

## Getting set up

```bash
make install-tools     # fetches golangci-lint, misspell and kind
make all               # fmt, vet, lint, test, build — the full local gate
```

`make all` is what CI approximates. If it passes locally, review should be about
design rather than mechanics.

## Building and running

```bash
make bin/triage-agent       # build the binary (no codegen)
./bin/triage-agent          # run against your current kubeconfig
make run                    # same, via the Makefile
make debug                  # with a debugger attached
```

The controller needs no special cluster setup — it derives virtual apps from
workload labels and annotations and streams cluster state to the core.

## Tests

Tests build a `fake.NewClientBuilder()` Kubernetes client; no cluster and no
downloaded test binaries are required.

```bash
make test          # all packages
```

To focus a single test:

```bash
go test -v ./push/... -run TestName
```

**Write the test against a real resource's observed status.** A fake-client
input passes easily and proves nothing — capture what the real object reports
first, then assert that.

## Two Go modules

This repository contains two:

| Path | Module | Notes |
|---|---|---|
| `.` | `github.com/triageagent-dev/agent` | the controller |
| `gcpevents/` | `github.com/triageagent-dev/agent/gcpevents` | a Cloud Run function, deployed from source |

`gcpevents` is separate so that `gcloud functions deploy --source ./gcpevents`
builds only the function. The consequence is that the root module's `./...` does
**not** reach it — it has its own CI job, and you must run its checks from inside
its directory:

```bash
cd gcpevents && go vet ./... && go test ./...
```

## Generated code

Commit the generated output with the change that caused it.

`gcpevents/catalog_gen.go` is generated by a tool in a sibling repository. It must
contain **service** data only — public Google product names and billing service
ids. Do not add project ids, account numbers, cluster names or any other
organisation-specific identifiers to it, and do not accept a regenerated version
that introduces them: a generated file is not read closely in review, which makes
it the easiest place for such data to enter a repository unnoticed.

## Documenting a decision

Anything non-obvious — a trade-off, a rejected alternative, a behaviour that looks
wrong until you know why — goes in an ADR under `docs/adr/`, numbered sequentially:

```markdown
# ADR-00NN: Title In Title Case

- **Date:** YYYY-MM-DD
- **Status:** Accepted

## Context
## Decision
## Consequences
```

Record *why*, including what you decided against and what it would cost to revisit.
An ADR that only restates the diff is not worth writing.

User-visible changes also get a `CHANGELOG.md` entry under `## [Unreleased]`,
following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Commits and pull requests

- Conventional commits: `feat(scope):`, `fix(scope):`, `docs(scope):`,
  `chore(scope):`, `ci:`. Use `!` for a breaking change.
- The subject says what changed; the body says **why**, and what the alternative
  was. Bug fixes should state the failure the fix prevents.
- Keep a PR to one concern. A drive-by cleanup in a behavioural change makes both
  harder to review and to revert.
- Never commit real identifiers — project ids, account numbers, billing accounts,
  cluster or tenant names, internal hostnames, secret paths. Use obvious
  placeholders (`example-project-0000`, `cluster-a`) in tests, fixtures and docs.
  Real values belong in deployment configuration outside this repository.

## Releasing

Tagging `v*` builds multi-arch binaries and publishes a GitHub release:

```bash
make release-tag        # or: git tag vX.Y.Z && git push <remote> vX.Y.Z
```

## Reporting bugs and vulnerabilities

Bugs: open an issue with the controller version, the flags or chart values in
use, and the behavior you observed versus expected. Security problems: see
[SECURITY.md](SECURITY.md) — please don't use a public issue.
